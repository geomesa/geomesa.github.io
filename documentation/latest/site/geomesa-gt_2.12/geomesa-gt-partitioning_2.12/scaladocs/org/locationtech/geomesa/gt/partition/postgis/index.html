  1.  class PartitionedPostgisDataStore extends DecoratingDataStore with HasAuthorizationsProvider

    Data store wrapper for partitioned postgis feature types.

    Data store wrapper for partitioned postgis feature types. This wrapper handles:

    Visibilities

    The physical schema carries a hidden per-row visibility column (_vis) as an ordinary attribute so that it flows through the sealed JDBCDataStore insert/read machinery for free. This wrapper hides that column from callers:

    • on createSchema, if the pg.vis.enabled user-data flag is explicitly true, a nullable _vis attribute is appended to the type before it's created
    • on read, features are re-typed to drop _vis; the MainView already filters rows by the caller's authorizations, and the visibility expression is surfaced into the feature user data
    • on write, the feature's visibility (from user data) is copied into _vis

    Feature type names

    The wrapped JDBCDataStore uses the name of the main view as the feature type name. Normally they are the same, but they will be different if a feature type has been renamed, or if attributes have been added or removed, which creates a new generation of the feature type backed by a new view. This wrapper maps feature type names to the current view, and hides the views for any previous generations.

    Feature ids

    The wrapped JDBCDataStore prefixes feature ids with the name of the main view. This wrapper removes the prefix, so that ids are stable across generations. Note that an id which itself starts with the name of the view is not supported, and may not be matched correctly.

    Default geometries

    The wrapped JDBCDataStore always uses the first geometry attribute as the default geometry. The default geometry that a feature type was created with is stored in the pg.geom.col user data, and this wrapper restores it in the feature types and features that it returns, and in any filters that reference the default geometry.

    For any type that has no physical _vis column (pre-existing schemas, or vis explicitly disabled), whose name matches its view, and whose default geometry is the first geometry attribute, features are passed through without being re-typed

    Multiple data store instances

    The mapping of feature type names to views is cached by each data store instance, for the duration configured by the geomesa.metadata.expiry system property. After updateSchema creates a new generation of a feature type, other data store instances (including ones in other processes) will keep reading from and writing to the view for the previous generation until their cache expires. The previous view does not expose the new generation, so those instances will not see anything written through the new view, although anything that they write will be visible through both views. Any feature source, reader or writer is bound to the view that was current when it was created, for as long as it is used, and will start to fail once that generation has been dropped.

    The mapping used to list feature type names is cached in the same way, but is re-loaded whenever the views in the database change - so a feature type that is renamed through a different data store instance will be listed under its old name until the cache expires.

  2.  class PartitionedPostgisDataStoreFactory extends DataStoreFactorySpi with LazyLogging

    Data store factory for the partitioned PostGIS store.

    Data store factory for the partitioned PostGIS store.

    Delegates to a standard JDBC-based factory to create the underlying JDBCDataStore, then wraps it in a PartitionedPostgisDataStore to manage the hidden per-row visibility column. We can't just subclass the JDBC factory and wrap in createDataStoreInternal, as JDBCDataStoreFactory.createDataStore is final and returns JDBCDataStore (which is itself final)
